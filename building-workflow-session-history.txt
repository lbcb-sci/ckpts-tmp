● Based on the README (raw reads → QC → gene-level counts, no DE analysis,
  simple local workflow), here are three good candidates for a small FASTQ test
  dataset:

  1. nf-core/test-datasets (rnaseq branch)

  - What it is: Paired-end FASTQ files purpose-built for testing RNA-seq
    pipelines (subsampled reads mapping to a small region, typically chr21 or
    similar).
  - Why suggested: It's designed for exactly this use case — validating a
    pipeline's mechanics (QC → alignment/quantification → counts) rather than
    doing real biology. Files are typically a few MB gzipped, well under the
    50MB limit, and pair naturally with a matching small reference genome subset
    also hosted in that repo, so you can build and test the whole pipeline
    end-to-end without downloading a full genome.
  - Tradeoff: Reads are already trimmed/curated for testing, so it's less
    representative of "messy" real-world raw reads (e.g., adapter contamination,
    variable quality) — less useful if you want to demo QC steps catching real
    issues.

  2. Galaxy Training Network (GTN) RNA-seq tutorial data

  - What it is: FASTQ subsets used in the GTN's "RNA-seq reads to counts"
    tutorial, hosted on Zenodo.
  - Why suggested: It's explicitly built around the same task shape as your
    README (raw reads → QC → gene counts), comes with a documented expected
    pipeline and known-good output, so you have a reference to sanity-check your
    own results against. Good size (small MB range), realistic (based on real
    biological data, subsampled).
  - Tradeoff: Requires pulling from Zenodo (fine, just noting it's a different
    host than GitHub).

  3. Griffith Lab RNA-seq tutorial data (chr22 subset)

  - What it is: A widely used teaching dataset (HCC1395 or similar) subsampled
    to reads aligning to chromosome 22 only.
  - Why suggested: Very well documented with a full walkthrough (useful if you
    get stuck), realistic paired-end human RNA-seq characteristics, and
    restricting to one chromosome keeps both the FASTQ and the reference genome
    small enough for fast local iteration.
  - Tradeoff: Tutorial-oriented framing may include assumptions (e.g., specific
    reference build) you'll want to double check against your own pipeline
    design.

  My recommendation: Option 1 (nf-core test-datasets) is the best fit for a
  first, simple version — it's minimal, purpose-built for pipeline mechanics,
  and pairs with a matching tiny reference, so you can get an end-to-end run
  working fastest. Option 2 is a strong second choice once you want to validate
  against known-good output.

  Let me know which one (or if you want me to check exact file sizes / URLs
  first) before I download anything.

     The README defines the goal: turn raw RNA-seq FASTQ reads into a

     analysis is

     (data/fastq/SRR6357070_{1,2}.fastq.gz, yeast, 50k read pairs) checked into

     Decisions made with the user for this revision:
     - Snakemake for orchestration (dependency-aware, incremental,
       multi-sample-ready).
     - Salmon (pseudo-alignment + quantification) instead of a genome aligner +
       featureCounts — simpler (no genome index/BAM sorting step), faster, and
       standard
       for count-matrix-only workflows that don't need read-level alignment
       positions.
     - pytximport to summarize Salmon's transcript-level quantification to the
       gene-level count matrix the README requires.
     - Repo structure fix: a plain top-level reference/ folder would wrongly
       imply
       it holds the canonical reference for the workflow. It doesn't — it's just
       the
       fixture paired with the test FASTQ. Test fixtures (FASTQ + reference) are
       grouped
       together under one clearly-scoped directory, and the workflow itself
       treats
       reference/sample paths as config-driven, not hardcoded.

     Repo structure change

     Rename data/ → test-data/ (git mv, preserves history) and add a reference
     subfolder there:

     test-data/
       fastq/
         SRR6357070_1.fastq.gz
         SRR6357070_2.fastq.gz
       reference/
         transcriptome.fasta   # transcript-level FASTA (Salmon indexes
     transcripts, not the genome)
         genes.gtf             # used to derive the transcript→gene mapping

     config.yaml (new) is the single place that names which FASTQ/reference
     paths the
     workflow runs against — for now it points at test-data/, but nothing in the
     Snakefile hardcodes that directory, so pointing it at a real dataset later
     is a
     config-only change, not a structural one.

     Reference files

     Both come from the same nf-core/test-datasets (rnaseq branch, reference/
     folder) that the test FASTQ itself is drawn from, so they're guaranteed to
     match:
     transcriptome.fasta (155KB) and genes.gtf (204KB). Tiny enough to check
     into git,
     same rationale as the FASTQ (reproducible without a network dependency).

     Tool choices

     - FastQC — raw-read QC.
     - fastp — adapter/quality trimming; also emits its own QC report

       trimmed
